Try someone@gmail.com in both fields (a real domain with mail servers — both pass, live and on submit). Then try a domain that doesn't exist, e.g. someone@zzzqqqxxx12345-totally-made-up-domain.com — it's a normal, well-formed address, so the format-only field accepts it both live and on submit, but the DNS/MX field rejects it both times, since no such domain can actually receive mail.
Note: someone@example.com and addresses on .invalid/.test are rejected by both fields regardless of the DNS/MX check — Pydantic's EmailStr itself treats those reserved placeholder domains (RFC 2606) as invalid syntax, so they're not useful for seeing the DNS/MX difference.
How it works
  • The two fields differ only in type — EmailStr vs. DeliverableEmailStr — nothing else in this form's code changes between them.
  • Both fields render from the same FormModel and validate on blur via the same LiveValidator/HTMX wiring as the Live HTMX Validation demo — this page's whole live-validation setup is one register_model_validator(EmailDnsComparisonForm) call, deriving the check straight from the model instead of hand-building a validator per field.
  • The DNS/MX lookup is a real network call, so it always runs server-side — there's no way to check MX records from browser JavaScript.
  • Because it's part of the type, submit-time validation enforces the same check automatically — a domain that fails live also fails on submit, with no separate rule to keep in sync.
  • The specific reason (bad TLD, no such domain, domain has no mail server, ...) comes straight from email-validator — it's shown in the results box above, on the input's hover tooltip, and in the submit-time error.

Add it to your own form in one line — no validator to build or register:

from pydantic_schemaforms import DeliverableEmailStr, Field, FormModel

class SignupForm(FormModel):
    email: DeliverableEmailStr = Field(..., title="Email")
